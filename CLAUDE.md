# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **Quarto book** — the textbook *"Introduction to Data Science"* (Python). The "code" is prose chapters in `.qmd` files containing executable Python code blocks. This is teaching material, not an application: the audience is beginners learning data science, so explanations should be clear and code should favor readability over cleverness.

## Commands

This project uses `uv` for Python dependency management (`pyproject.toml` + `uv.lock`).

- **Render the whole book:** `uv run quarto render` → output in `_book/`
- **Live preview while editing:** `uv run quarto preview` (auto-rebuilds on save)
- **Render a single chapter:** `uv run quarto render descriptive_stats_and_plots.qmd`
- **Install/sync deps:** `uv sync`

Publishing is automated: pushing to `main` triggers `.github/workflows/publish.yml`, which renders and deploys to the `gh-pages` branch.

## Chapter structure

`_quarto.yml` defines the book and the **chapter order** — a new chapter only appears in the book if it is added to the `chapters:` list there. Chapters render in listed order:

1. `index.qmd` (welcome) → `introduction.qmd` → `python_basics.qmd` → `descriptive_stats_and_plots.qmd` → `array_computations.qmd` → `data_tables.qmd` → `data_visualization.qmd` → `interactive_visualizations.qmd` → `maps.qmd` → `iteration_and_functions.qmd` → `statistical_inference.qmd` → `hypothesis_testing.qmd` → `confidence_intervals.qmd` → `classification.qmd` → `linear_regression.qmd` → `unsupervised_learning.qmd` → `web_data.qmd` → `where_next.qmd`

The chapters from `data_tables.qmd` onward are stubs to be filled in. Each chapter covers roughly two sessions of the Fall-2025 class (see the mapping comments at the top of each stub); `interactive_visualizations.qmd` and `maps.qmd` split classes 14–15 and deliberately come before `iteration_and_functions.qmd` to match the class order, and the inference chapters depend on loops/functions from the iteration chapter. `web_data.qmd` is the one chapter with **no** matching class material — it is drafted from scratch and sits late so it can use loops, functions, and DataFrames; its scraping cells must target a stable site with a saved fallback (see the note in the stub).

## Authoring conventions

- **Executable Python blocks use the `{python}` fence** — ` ```{python} ` — not a plain ` ```python `. The curly braces are what makes Quarto execute the block and embed its output. A recurring past bug was blocks failing to run because the braces were missing.
- Code in a chapter shares one kernel session top-to-bottom: variables defined in an early block are available in later blocks. Chapters typically load a dataset once at the top and reference its variables throughout.
- **Voice and tone: warm but precise, approachable but not chatty.** Friendliness should come from *directness and concreteness* — address the reader as "we" in body prose and reserve "you" for instructions and exercises (see the naming-and-explicitness bullet below, which the author's edits to `data_tables.qmd` establish); introduce a concept with a concrete example or problem before naming and defining it; define jargon on first use; prefer concrete nouns. Do **not** reach for casual diction: avoid filler intensifiers ("really", "pretty", "super", "a lot"), idioms/clichés ("got the job done", "under the hood", "the heart of", "shines"), colloquial evaluative adjectives ("clunky", "neat", "handy", "nice", "messy"), vague hedges ("basically", "sort of"), jokes/emoji, and forced reassurance ("don't worry, this is easy"). Keep/cut test: phrasing that signals *closeness* (a concrete noun, a named method or property, a worked number, an honest "this takes practice") stays; phrasing that signals *looseness* (an intensifier, idiom, slang adjective, hedge, or joke) goes. Note that direct "you" and plain imperatives count as closeness only inside exercises; in body prose the author converts them to "we" and to statements. The `chapter-editor` agent enforces this and can run a dedicated tone pass.
- **Name things explicitly; do not lean on pronouns, ellipsis, or deixis.** This is the single largest difference between generated drafts and the author's revisions of them, measured across the author's edits to `data_tables.qmd`. Four habits, with real before/after pairs from that chapter:
  - **Call an API element what it is.** Write "the `.shape` **property**", "the `.idxmax()` **method**", "the `how=` **argument**", usually with a leading "The". Not "`.shape` gives the number of rows" but "The `.shape` property gives the number of rows"; not "Pandas offers `.query()`" but "Pandas also has a `.query()` method".
  - **Replace a pronoun or a demonstrative with the noun it stands for**, even at the cost of repetition. "That check is worth performing every time you merge" → "Checking the size of the DataFrames before and after a join is worth performing every time we join DataFrames." Likewise "`.dropna()` removes the rest" → "removes any rows that contain missing data"; "the rows that matched on both sides" → "on both DataFrames"; "the result" → "the result DataFrame".
  - **Do not drop a noun that could be repeated.** "A Series holds one column. Most data has many, and they are rarely all the same kind of thing." → "A Series holds one column *of data*. Most data has many *columns*, and they are rarely all the same kind of *data*."
  - **Say which operation produced the output being discussed.** "The left-hand column is the Index" → "*When we call the `.head()` method,* the left-hand column is the Index." Similarly "There is a lot in that summary" → "The output shows that…", and "That is 360,771 flights" → "As we can see from this output, there are 360,771 flights".
- **Prefer "we" to "you", and a statement to an instruction, in body prose.** Across the author's revision of `data_tables.qmd`, "we" rose sharply and "you" fell. "Rows work the same way" → "We can extract a subset of rows in the same way"; "We build one by handing pandas the values" → "We can create pandas Series by handing pandas the values"; "Use whichever makes a line easier to read" → "Using whichever makes a particular code easier to read is generally preferred." Exercises still address the reader directly as "you".
- **Add the clause that says why a result matters, or what it does not disturb.** The author's edits repeatedly extend a sentence rather than trimming it, and revised paragraphs run slightly *longer* than the generated ones (median sentence 16 → 18 words). "gives the label of the largest value rather than its position:" → "…rather than its position *which can be much more informative*:"; "Arithmetic applies to every value at once:" → "…at once *and the Index labels remain unchanged*:". Terseness is not a virtue here; unexplained terseness is the defect.
- **Attach units and clarifying appositives to numbers and terms.** "the median is **−3**" → "the median *(50% percentile)* is **−3** *minutes*"; "`gas_prices` held 52 numbers" → "held 52 *prices as* numbers". Capitalize the library's proper nouns: **Index**, **Series**, **DataFrame**, and say "DataFrame" rather than "table" when referring to the object rather than the concept.
- **Cut editorial asides and rhetorical lead-ins.** Sentences whose work is to set up a tone rather than convey information get removed. "There is a lot in that summary." and "this book uses masking by default, because it is what you will encounter most often" were both cut; the second became simply "generally preferred". Do not tell the reader what the book prefers or what is most common in the wild unless it changes what they should do.
- **Register: this is a textbook, so write in complete, connected sentences.** The failure mode to avoid is *telegraphic* prose: clipped fragments and two- or three-word sentences used for punch, which read as magazine copy rather than as teaching material. Spell the thought out and supply the connective rather than leaving the reader to infer it. Worked examples of the fix, all from `introduction.qmd`:
  - "Four names, four eras." → "Each of these four names dominated a different era."
  - "Analyzing data is old. The name is not." → "The practice of analyzing data is very old, but the name given to it here is recent."
  - "Then it drifted." → "Over time, however, its estimates drifted away from reality."
  - "Now the plot:" → "With the contents of the file established, we can plot how the popularity of individual names has changed over time:"
  - "The harms stopped being hypothetical." → "Together these accounts established that the potential harms of predictive modeling were not hypothetical."

  This is **not** a mandate for uniformly long sentences, which is its own AI-prose tell (see the next bullet). Short sentences are correct where they carry real content rather than rhetorical punch: definitions ("He called this **literate programming**."), exercise instructions ("For each stage, write one sentence."), and statements of result in solutions ("The third cell still prints `3.25`."). The test is whether the brevity is doing work or performing emphasis.
- **Avoid prose mannerisms that read as AI-generated.** The biggest tell is the **em dash (—) used as a parenthetical or appositive break** ("arrays — the foundation of NumPy — are..."); rewrite with a comma, a colon, a period splitting the sentence, or parentheses instead. An occasional em dash for a genuine interruption or sentence break is fine, but more than one or two per page is a sign of overuse — restructure the sentence rather than reaching for the dash by default. Also avoid: triplet lists used as a rhythmic crutch ("clearer, faster, and more powerful"), "Let's" as a sentence-opener more than once or twice a chapter, throat-clearing transitions ("It's worth noting that...", "In other words..."), and a too-tidy three-beat cadence on every paragraph. Vary sentence length and structure the way a human writer drafting over multiple sittings would, rather than producing uniformly polished paragraphs.
- **Watch the antithesis clincher.** A distinct tic, easy to produce and hard to notice, is ending paragraph after paragraph on a contrastive turn: "X, not Y", "is not the same thing as", "rather than", "which is the point". A first draft of `introduction.qmd` closed sixteen paragraphs this way. Any one of them is fine; the accumulation reads as a metronome. When a section shows the pattern, rewrite roughly a third of the offenders to end on a plain factual statement instead. The related hedge-frame "it is worth noting / worth knowing / worth doing" should appear at most two or three times in a chapter.
- Concepts are built progressively. `descriptive_stats_and_plots.qmd` deliberately uses **base Python + Matplotlib only** (lists, not DataFrames) because Pandas hasn't been taught yet — when editing a chapter, only use tools introduced in it or earlier chapters.
- **Illustrations are built with Matplotlib/NumPy, not external images**, with the drawing code hidden via `#| echo: false` so only the figure renders (see the axis-layout and RGB-mixing diagrams in `array_computations.qmd` for the pattern). When a concept is spatial or structural (array shapes, axes, a transformation, a color model), prefer building a diagram this way over describing it in prose alone. The `chapter-student` and `chapter-editor` agents both review illustrations as part of a chapter review: whether each one is easy to understand, and whether a passage would benefit from an illustration that doesn't exist yet.
- **In-figure text placement.** Center each label within the region it names — compute the position from the same geometry that draws the figure (a mask's centroid, a box's center) rather than hand-tuning coordinates, so labels stay correct if the figure changes. A label for an arrow or axis belongs at its midpoint, rotated to run along it. Labels must not hug edges, cross other elements, or collide with wireframes. Use the same notation in the figure as in the surrounding code and output: if the prose discusses `shape = (648, 960, 3)`, the diagram's arrows should carry the matching names (height, width, channel). Always view the rendered PNG after changing a figure — label placement can't be judged from the drawing code.
- **Show the data before computing on it.** After a chapter loads a dataset, display a few values and plot it (with tools already taught) *before* any statistics; the story the plot establishes ("prices peaked in April") is what the later computations then confirm. Data-loading cells stay **visible** with a brief "you don't need to understand the details yet" note (the ch. 3–4 pattern), never hidden with `#| echo: false` — a reader following along must be able to create every variable the chapter uses from code they can see.
- **Verify every numeric claim against actual output.** Any sentence that interprets a result — in body prose or an exercise solution ("the IQR is smaller than the standard deviation") — must be checked by running the code or reading the rendered output, never written from expectation. Likewise, a code comment must describe what the code *now* does; stale comments left from an earlier version of an example (a "10% discount" comment above `+ 3`) are a recurring bug and destroy a learner's trust in the solutions.
- **The same rule applies to factual and historical claims.** Dates, attributions, and anecdotes must be checked against a source before they are written, not recalled. Anything that cannot be confirmed gets **cut rather than hedged** — a vaguer sentence is not a fix for an unverified one. Widely repeated stories are the most dangerous, because they circulate in subtly wrong forms (a draft of `introduction.qmd` had the 2002 Oakland A's winning the World Series, which they did not).
- **Verify forward references before promising them.** A sentence of the form "by @sec-x you will be able to do this yourself" is a claim about another chapter, and it must be checked by opening that chapter. A draft of `introduction.qmd` promised that ch. 3 would teach the teaser code, but ch. 3 converts DataFrames to lists and explicitly tells the reader to ignore the pandas, and the `for` loop is postponed to @sec-iteration-functions. Broken promises of this kind are invisible when the chapter is read alone and destroy trust when the reader arrives and finds nothing.
- **Static, hand-placed images (not code-generated) go in the top-level `images/` directory**, which is tracked in git (unlike `data/`). Reference them with a normal relative path, e.g. `![](images/cover_img.png){width="300px"}` as `index.qmd` does for the book cover. **Every image placed in `images/` must have a corresponding entry in `images/SOURCES.md`** recording where it came from (source URL) and its license — add the entry in the same change that adds the image.
- **End most sections with an exercise.** The established pattern (see ch. 2–4) is one exercise at the end of each content section, plus a consolidated `## Exercises` section at the chapter's end. Each exercise is a `::: {.callout-tip title="Exercise" #exercise-<chapter>-<slug>}` block followed by a collapsible `::: {.callout-note title="Solution" #solution-<chapter>-<slug> collapse="true"}` block. An exercise must only use tools introduced up to that point in the chapter. Pure setup sections (e.g. loading the dataset) can be skipped.
- Datasets are loaded by URL (e.g. the FiveThirtyEight Bechdel CSV) so the GitHub Actions renderer can fetch them without committed data. The local `data/` directory is gitignored, with three exceptions listed in `.gitignore`: the gas-price snapshot, `data/babynames/`, and `data/nycflights/`. The latter two are datasets the book publishes rather than borrows, so both the generated files and the scripts that generate them are tracked.
- **`data/babynames/` is a dataset the book publishes rather than borrows.** The baby-name data used in `introduction.qmd` is built from Social Security Administration sources by `data/babynames/make_babynames.py`, committed to this repo, and loaded from its own `raw.githubusercontent.com` URL. See `data/babynames/README.md` for the schema, the sources, and how to rebuild when the SSA adds a year. Two consequences: regenerated files must be pushed before a render will pick them up, and the figures `introduction.qmd` quotes for the most recent year need rechecking after any rebuild.
- **`data/nycflights/` is the other published dataset, and works the same way.** The flight-delay data used in `data_tables.qmd` is built by `data/nycflights/make_nycflights.py` into four files: `flights.csv.gz`, `airlines.csv`, `weather.csv.gz` and `airports.csv`. All four are loaded from `raw.githubusercontent.com` URLs, so **regenerated or newly added files must be pushed before a render will resolve them** — a chapter cell pointing at an unpushed file fails the build. Rebuilding the flights file downloads roughly 360 MB from the BTS; `--parts weather airports` rebuilds just the two small files in seconds and reads the airport list back out of the existing `flights.csv.gz`. Every source is public domain (BTS, NOAA/NWS via the Iowa Environmental Mesonet, and OurAirports) so the data can ship with the book; see `data/nycflights/README.md` for the schemas, the licensing, and why OpenFlights was deliberately rejected. `data_tables.qmd` quotes many specific figures from this data, so all of them need rechecking after any rebuild.
- Much of the book's material derives from an introductory data science class the author teaches. Relevant source material from that class lives in `extras/` (e.g. class slides, code, notebooks) — **consult these files when developing new chapters or sections**, as they're a primary source for the book's content even though they aren't rendered into it.
  - `extras/material_from_2025f/` holds the notebooks (`class_code/`) and slides (`slides/`) from the **most recent** time the class was taught (Fall 2025) — prefer it over the older `extras/class_notebooks/` and `extras/*_2024f.pdf` material. The class-N notebook usually maps to a book chapter (e.g. `class_06`/`class_07` ≈ the array-computations chapter); `*_answers.ipynb` versions include worked solutions.

## Not part of the book

- `cut_could_be_added_later.qmd`, `notebooks/` — scratch/reference material. Not in `_quarto.yml`, not rendered. Don't treat these as authoritative.
- `creation_pieces/` — a holding area for generated drafts/sections the author isn't using yet but wants to keep (e.g. `array_computations_v1.qmd`, an earlier version of a chapter). Not in `_quarto.yml`, not rendered. Reference for alternative drafts, not authoritative.
- `_book/`, `_freeze/`, `.quarto/`, `*_files/` — generated render artifacts.
- `main.py` — leftover project scaffold, unused.
